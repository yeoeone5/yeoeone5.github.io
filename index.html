AI로 빠르게 만들고, 결과는 직접 확인합니다.

코드는 AI 코딩 도구로 만들고, 실행·운영·검증·판단은 제가 합니다. 아래는 그렇게 진행한 졸업프로젝트와, 직접 운영 중인 서비스 두 개의 기록입니다.

GitHub

일하는 방식

  1. 요구를 먼저 정리

    무엇을, 어떤 기준으로 확인할지 먼저 적고 AI에게 맡깁니다.

  2. AI로 만들기

    수집기, 점검 쿼리, 학습 코드를 AI 코딩 도구(Claude)로 만들었습니다.

  3. 직접 돌리고 운영하기

    9월 11일부터 5분 수집기를 운영하며 모니터링으로 오류를 잡았습니다.

  4. 결과를 의심하고 검증하기

    숫자가 맞는지 Excel로 다시 계산하고, 모델은 단순한 기준선과 비교했습니다.

AI가 만든 결과가 "그럴듯해 보이는 것"과 "맞는 것"은 다릅니다. 그 차이를 확인하는 게 제 일이라고 생각합니다.

프로젝트: 소아 응급실 병상 예측 (졸업프로젝트, 팀 Sync 3명, AI 파트)

문제

아이가 아파 응급실에 가도 소아 병상이 없으면 다른 병원으로 다시 옮겨야 합니다. 공공 API의 실시간 병상 수는 '지금' 값일 뿐이라, 도착 시점(예: 30분 뒤)의 소아 병상을 예측하는 서비스를 만들고 있습니다.

124곳
수집 대상 응급실 (소아 병상 운영 41곳)
5분
수집 주기
약 153만 건
병원별 관측 (9/11 ~ 11/2)
4건
점검 쿼리 8개로 찾은 데이터 품질 이슈

데이터 흐름

  1. 공공 API(국립중앙의료원)
  2. 5분 수집기(Python)
  3. SQLite 저장 + 원본 JSON 보관
  4. SQL 점검 8개
  5. 예측 모델 검증(LightGBM vs 기준선)

AI가 만든 것을 검증한 사례 3가지

사례 1. 수집기가 멈춰 있던 시간 찾기

상황
AI로 만든 수집기를 운영하는 중, 기록이 비는 구간이 있었습니다.
확인
SQL의 LAG 함수로 직전 수집 시각과의 간격을 계산해 15분 넘게 빈 구간을 찾았습니다. 86건(서울 52, 경기 34), 가장 긴 공백은 약 285시간이었습니다.
결과
스케줄러 경로를 고치고, 공백을 감지하도록 바꿨습니다.
WITH r AS (
  SELECT stage1, ts,
         LAG(ts) OVER (PARTITION BY stage1 ORDER BY ts) AS prev_ts
  FROM runs WHERE ok = 1)
SELECT stage1, prev_ts, ts,
       ROUND((julianday(ts) - julianday(prev_ts)) * 1440) AS gap_min
FROM r
WHERE gap_min > 15        -- 15분 초과만
ORDER BY gap_min DESC;

사례 2. 저장된 값과 원본이 달랐던 문제

상황
정원 필드 이름이 명세(HVS02)와 달리 소문자(hvs02)로 와서, 9/11~9/30 데이터 100,554건이 저장되지 않았습니다.
확인
원본 JSON과 저장된 값을 날짜별로 비교해 누락 기간과 건수를 확정했고, 결과를 Excel로 다시 계산했습니다.
결과
대소문자를 통일하고, 보관해 둔 원본 JSON에서 복원했습니다.

사례 3. 오차는 줄었는데 결과는 나빠진 모델

상황
LightGBM 모델이 값이 바뀐 구간의 오차(MAE)를 1.287석에서 1.249석으로 2.9% 줄였습니다. 숫자만 보면 개선입니다.
확인
'30분 뒤에도 지금과 같다'는 기준선과 비교하고, 보호자가 실제로 겪는 '헛걸음'(자리 있다고 했는데 도착하면 0석)을 따로 셌습니다. 헛걸음이 616건에서 638건으로 늘었습니다.
결과
"아직 기준선을 넘지 못했다"고 팀에 그대로 보고했고, 팀은 헛걸음률을 메인 지표로 정했습니다.
지표 (30분 뒤, test 58,000건)기준선모델 v1
오차, 값이 바뀐 구간 (MAE)1.287석1.249석
오차, 전체 (MAE)0.274석0.276석
헛걸음 건수616건638건
놓침 건수601건568건

병원 ID를 빼고 학습해도 결과가 거의 같아, 모델이 병원을 외운 것은 아님을 확인했습니다.

직접 운영 중인 서비스 2개

동아리 사람들이 실제로 쓰고 있는 웹앱 두 개를 만들어 운영하고 있습니다. 코드는 Claude Code로 만들었고, 규칙 설계·배포·운영·문제 대응은 제가 합니다.

1. 벌크업 인증앱

검도부 지인 약 8명이 6개월 동안 운동을 인증하고, 매달 마지막 날 랭킹을 보는 웹앱

기간
2026년 8월 3일 시즌 시작, 지금도 운영 중 (시즌 종료 2027년 1월 31일)
링크
https://bulkup-ekum.vercel.app (카카오 로그인이 필요합니다)
기술
HTML · CSS · JavaScript (프레임워크 없음), Supabase (Postgres, 로그인, 사진 저장), 카카오 로그인, Vercel, 홈 화면에 추가해 쓰는 웹앱(PWA)
설계 원칙
인증률과 랭킹 계산은 전부 DB 뷰에서 하고, 화면은 보여 주기만 합니다. 누가 무엇을 볼 수 있는지는 RLS 정책으로 막습니다.

운영하며 고친 것

1. 날짜가 하루 밀린 문제
상황
8월 6일 아침, 인증 화면에 전날 날짜(8월 5일)가 떴습니다.
확인
오전 9시 전에만 생기는 문제였고, 화면 코드와 DB(서버는 UTC 기준) 양쪽에 원인이 하나씩 있었습니다. 낮에 테스트하면 멀쩡해 보여서 늦게 발견됐습니다.
결과
날짜를 모두 한국 시간 기준으로 바꾸고, 같은 실수를 grep으로 찾아내는 점검 방법을 문서에 남겼습니다.
2. 일부 사람만 식단 화면이 안 열린 문제
상황
9월에 몇몇 참가자만 식단 기록이 안 된다는 이야기가 나왔습니다. 제 계정에서는 재현되지 않았습니다.
확인
'선택'이라고 안내한 식단 목표를 건너뛴 사람만 DB에서 기록이 거절되고, 화면은 그 탭을 조용히 잠그고 있었습니다.
결과
목표가 없어도 기록되도록 DB와 화면을 같이 고쳤습니다. 한쪽만 고치면 다시 막힌다는 점도 문서에 적었습니다.
3. 이미 발표한 결과가 바뀔 수 있었던 규칙 수정
상황
참가자 제보로, '20분 이상 운동만 인정' 규칙이 원래보다 이른 8월 10일부터 적용돼 일부 기록이 빠진 것을 알았습니다.
확인
시작일을 옮기면 이미 발표한 월간 랭킹까지 다시 계산되기 때문에, 옮기기 전에 누가 며칠 늘어나는지, 미달에서 통과로 바뀌는 달이 있는지를 쿼리로 먼저 뽑아 봤습니다.
결과
영향을 확인한 뒤 시작일을 9월 1일로 옮겼습니다.

2. 검도부 출결 관리

검도부 정규운동 출석을 GPS로 확인하는 웹앱. 부원은 도장 반경 500m 안에서 출석 버튼을 누르고, 임원진 4명은 전체 명단과 누적 통계를 봅니다.

기간
2026년 9월부터 사용 (11월 21일부터 검도부 휴동 기간이라 쉬는 중)
사용자
사범님 포함 25명이 사용했고, 중간에 휴동한 2명을 빼면 현재 23명
링크
https://kendo-attendance.vercel.app (부원 전용, 카카오 로그인이 필요합니다)
기술
React · TypeScript · Vite, Supabase (Postgres, 로그인), 카카오 로그인, Vercel, PWA
설계 원칙
출석·지각 판정은 화면이 아니라 서버 함수가 합니다. 서버 시각과 서버에 저장된 도장 좌표로 거리와 시간을 다시 계산하므로, 화면에서 "출석입니다"라고 보낼 수 없습니다. 일반 부원은 RLS 정책 때문에 본인 기록만 받아 볼 수 있습니다.

운영하며 고친 것

1. 도장 좌표가 약 900m 어긋난 문제
상황
처음 도장 좌표를 주소를 보고 눈대중으로 잡았는데, 경도가 약 900m 어긋나 있었습니다. 반경을 500m로 잡았기 때문에 그대로 두면 도장에 있어도 출석이 안 됩니다.
확인
OpenStreetMap에 등록된 건물 중심 좌표와 비교했습니다.
결과
좌표를 보정하고, 좌표를 바꿀 때는 도장에서 실제 거리 표시를 확인하라고 문서에 남겼습니다.
2. 출결 집계를 흔들지 않는 '기록용 출석'
상황
배정 요일이 아닌 날 도장에 나온 것도 남길 방법이 필요했습니다.
확인
정식 출석 기록과 섞으면 결석 계산이 흔들린다는 점을 확인했습니다.
결과
위치 확인 없이 남기는 개인 기록을 별도 테이블로 분리해, 출결 집계에는 들어가지 않게 만들었습니다.
